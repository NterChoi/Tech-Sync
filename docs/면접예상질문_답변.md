# Tech-Sync 구술/면접 예상질문 답변 정리

> 본인 프로젝트(`com.techsync`) 실제 코드 기준으로 작성. 핵심은 "내 프로젝트에선 이렇게 했고, 왜 그랬는지" 한 문장으로 말할 수 있게 하는 것.

---

## 공통 질문

### 1) 전체 패키지 구조
`com.techsync` 아래 **계층형(Layered) 구조**로 분리했습니다.

- `TechSyncApplication` — 진입점(main)
- `config` — 설정/인프라: `SecurityConfig`, `JwtProvider`, `JwtFilter`, `RedisConfig`, `WebSocketConfig`, `RestTemplateConfig` 등
- `controller` — HTTP/WebSocket 요청 진입점: `AuthController`, `UserController`, `FeedController`, `KeywordSubscribeController`, `AlarmController`, `WorkspaceController`, `EditorWebSocketController`
- `service` — 비즈니스 로직(인터페이스 + `~Impl` 구현 분리): `AuthService/AuthServiceImpl` 등, 외부 수집기 `NaverNewsCollectorService`
- `repository` — 데이터 접근(Spring Data JPA / Mongo): `UserRepository`, `ArticleRepository` …
- `domain` — JPA/Mongo Entity: `User`, `Article`, `Keyword`, `Workspace`, `Alarm` 등
- `dto` — 요청/응답 전용 객체(대부분 `record`): `SignupRequest`, `AuthResponse`, `ApiResponse<T>` …
- `exception` — `BusinessException`, `GlobalExceptionHandler`

> 핵심: **요청 → Controller → Service → Repository → DB** 단방향 의존. 저장소는 MariaDB(JPA) + MongoDB + Redis를 함께 씁니다.

### 2) Controller / Service / Repository 역할 차이
- **Controller**: HTTP 요청을 받고 응답을 돌려주는 "입출구". 요청 DTO 바인딩·검증(`@Valid`), 상태코드 결정만 하고 로직은 Service에 위임.
- **Service**: 실제 **비즈니스 로직**. 검증(중복 이메일), 비밀번호 암호화, 토큰 발급, 트랜잭션 경계(`@Transactional`)를 담당.
- **Repository**: DB 접근만 담당. JPA 인터페이스로 CRUD/조회 쿼리를 추상화.

### 3) 가장 중요한 기능의 요청 흐름 — 실시간 동시 편집 (메인 핵심 기능)
> 로그인은 부차적 기능이고, 프로젝트의 핵심은 여러 명이 한 문서를 동시에 편집하는 **실시간 협업 에디터**입니다. HTTP 단발 요청이 아니라 **STOMP over WebSocket(연결 기반)** 이라 단계가 나뉩니다.

**① 연결 + 인증 (CONNECT)**
1. 워크스페이스 진입 → 프론트가 SockJS로 `/ws` 에 STOMP **CONNECT**, 헤더 `Authorization: Bearer {accessToken}`
2. `StompAuthChannelInterceptor.preSend()` 가 CONNECT 프레임을 가로채 **JWT 검증** → 유효하면 userId/email로 `UsernamePasswordAuthenticationToken` 생성 후 `accessor.setUser()` (실패 시 연결 거부). 이후 메시지의 `Principal` 이 됨

**② 구독 (SUBSCRIBE)**
3. 클라이언트가 `/topic/workspace/{id}/edit`, `/topic/workspace/{id}/cursor` 구독

**③ 편집 발신 (SEND)**
4. 글자 입력 → 변경분(delta)만 `/app/edit/{workspaceId}` 로 SEND. payload = `DeltaMessage(ops, clientSeqNo)` — 전체 문서가 아니라 **변경 연산(ops)만** 전송

**④ 서버 처리 (핵심)**
5. `EditorWebSocketController.edit()` (`@MessageMapping("/edit/{workspaceId}")`) → Principal에서 userId 추출 → `EditorServiceImpl.applyDelta()`:
   - **멤버 인가 검증** (`existsByWorkspaceIdAndUserId`) → 아니면 403
   - **Redis `INCR`** 로 워크스페이스별 전역 순번 `seqNo` 채번 → **동시 편집 순서를 단일 지점에서 직렬화**(핵심)
   - **MongoDB `DELTA_LOG`** 에 delta 저장(`workspaceId+seqNo` 유니크 인덱스, append-only 이벤트 로그)
   - `DeltaBroadcast` 생성 → `SimpMessagingTemplate.convertAndSend("/topic/workspace/{id}/edit", ...)` 로 **구독자 전원에게 fan-out**

**⑤ 수신 (브로드캐스트)**
6. 같은 워크스페이스 구독자들이 broadcast 수신 → 본인 화면에 delta 적용. 발신자는 `clientSeqNo` 로 자기 변경의 echo(ack) 식별

**⑥ 커서 / 영속화**
7. 커서 이동은 `/app/cursor/{id}` → `/topic/.../cursor` 동일 패턴이되 **DB 저장 없이 휘발성 브로드캐스트만**
8. 편집 결과는 REST(`saveSnapshot`)로 MongoDB `DraftSnapshot` 에 저장, 버전은 `DraftVersion` 에 누적

**설계 포인트(강조)**: STOMP over WebSocket / **Redis INCR로 seqNo 채번해 동시성 충돌 순서 정렬** / delta만 전송 + Mongo append-only 로그 / 인증은 CONNECT 1회 + 메시지마다 멤버 인가.

> (참고) 로그인 흐름: `POST /api/auth/login` → `AuthServiceImpl.login()` 에서 `findByEmail` 조회 + `passwordEncoder.matches` 검증 → JwtProvider로 Access/Refresh 발급 → Refresh를 Redis(`refresh:{userId}`, 7일 TTL)에 저장 → `AuthResponse` 반환 → 프론트가 localStorage 저장 후 `Authorization: Bearer` 로 사용.

### 4) 가장 중요한 Controller
프로젝트 핵심 기능(실시간 동시 편집)을 담당하는 **`EditorWebSocketController`** 입니다. STOMP 메시지를 받는 `@Controller` 로, 편집 delta(`@MessageMapping("/edit/{workspaceId}")`)와 커서(`/cursor/{workspaceId}`)를 처리합니다.
> (REST 기준으로 가장 중요한 건 인증의 시작점인 `AuthController`(`/api/auth`) 라고 덧붙이면 좋습니다.)

### 5) 주요 메서드의 입력/반환 — `EditorWebSocketController.edit()`
- 어노테이션: `@MessageMapping("/edit/{workspaceId}")` — 클라이언트가 `/app/edit/{workspaceId}` 로 보낸 STOMP 메시지를 매핑
- 입력:
  - `@DestinationVariable Long workspaceId` — 목적지 경로의 워크스페이스 ID
  - `@Payload @Valid DeltaMessage message` — 본문. `ops`(변경 연산 리스트, `@NotEmpty`)와 `clientSeqNo`(클라이언트 순번, `@NotNull @PositiveOrZero`)
  - `Principal principal` — CONNECT 때 STOMP 인터셉터가 심어둔 인증 주체(여기서 userId 추출)
- 반환: **`void`**. HTTP처럼 호출자에게 직접 응답하지 않고, 서비스가 `/topic/workspace/{id}/edit` 토픽으로 **구독자 전원에게 브로드캐스트**합니다(발신자도 구독 중이라 echo로 받아 ack 처리).
- 실패: 멤버가 아니면 `BusinessException(403)`, 인증 정보 없으면 401.
> 대조용 REST 예: `AuthController.login()` — 입력 `@Valid @RequestBody LoginRequest`(email, password), 반환 `ResponseEntity<ApiResponse<AuthResponse>>`(accessToken/refreshToken/userId/name), HTTP 200.

### 6) Service의 비즈니스 로직
**핵심 — `EditorServiceImpl` (동시 편집)**
- `applyDelta`: 멤버 인가 검증 → Redis INCR로 seqNo 채번(순서 직렬화) → MongoDB DELTA_LOG 저장 → 토픽으로 브로드캐스트
- `broadcastCursor`: 멤버 검증 후 커서 위치를 토픽으로 휘발성 브로드캐스트(저장 X)
- `saveSnapshot`/`getSnapshot`: 현재 문서 상태를 DraftSnapshot에 upsert/조회
- `saveVersion`/`getVersions`/`getVersion`: 버전 번호를 1씩 증가시켜 DraftVersion에 누적·조회

**인증 — `AuthServiceImpl`**
- 회원가입: 이메일 중복 검사 → 비밀번호 BCrypt 암호화 → 저장
- 로그인: 사용자 조회 + 비밀번호 매칭 → 토큰 발급 → Redis에 refresh 저장
- 토큰 재발급: 토큰 유효성 + Redis 저장값 일치 검증 → 새 토큰 발급
- 로그아웃: Redis의 refresh 토큰 삭제
- 아이디 찾기: 이름으로 조회 후 이메일 **마스킹** / 비밀번호 재설정: 이메일+이름 본인확인 → 암호화 저장 → refresh 무효화

### 7) Repository와 Entity 연결
각 Repository는 제네릭으로 Entity와 묶입니다. 예: `UserRepository extends JpaRepository<User, Long>` → **User** 엔티티, PK 타입 Long. 마찬가지로 `ArticleRepository`↔Article, `KeywordRepository`↔Keyword, `WorkspaceRepository`↔Workspace 등.

### 8) 구현 코드 없는 Repository가 동작하는 이유
Spring Data JPA가 애플리케이션 구동 시 인터페이스를 보고 **프록시 구현체를 런타임에 자동 생성**해 빈으로 등록하기 때문입니다. 메서드 이름(`findByEmail`)을 파싱해 JPQL/SQL을 만들어 줍니다(쿼리 메서드).

### 9) Entity 하나 설명 — `User`
- `@Entity @Table(name="USER_INFO")` — USER_INFO 테이블 매핑
- `@Id @GeneratedValue(IDENTITY)` `USER_ID` — AUTO_INCREMENT PK
- `email`(unique, not null), `password`, `name` 컬럼
- `@CreatedDate`/`@LastModifiedDate` + `AuditingEntityListener` 로 생성/수정 시각 자동 기록
- 무분별한 setter 대신 `updateName()`, `updatePassword()` 같은 의미 있는 메서드만 노출(불변성 보호)

### 10) Entity와 DTO를 분리한 이유
- **DB 구조(Entity)와 API 스펙(DTO)을 독립**시키기 위해. 컬럼이 바뀌어도 API 응답을 그대로 유지 가능
- 비밀번호 같은 **민감 필드 노출 차단**(엔티티엔 password가 있지만 응답 DTO엔 없음)
- 엔티티를 그대로 직렬화하면 지연로딩/순환참조 문제가 생김 → DTO로 필요한 값만 전달

### 11) 요청 DTO / 응답 DTO 분리 이유
- 요청과 응답은 **필드가 다름**. 예: 로그인 요청은 email/password, 응답은 token/userId/name
- 요청 DTO엔 `@NotBlank @Email` 같은 검증을, 응답 DTO엔 그런 게 불필요
- 역할이 섞이면 불필요한 필드가 노출되거나 검증이 꼬임

### 12) DTO 없이 Entity를 그대로 반환한 곳?
없습니다. 모든 컨트롤러가 응답 DTO(`AuthResponse`, `UserResponse` 등)를 `ApiResponse<T>` 로 감싸 반환합니다. (만약 엔티티를 그대로 반환했다면 → 비밀번호 노출, 지연로딩 직렬화 예외, API가 DB 스키마에 종속되는 문제가 생깁니다.)

### 13) `@RestController` vs `@Controller`
- `@Controller`: 주로 뷰(HTML) 이름을 반환. 데이터를 반환하려면 메서드마다 `@ResponseBody` 필요
- `@RestController` = `@Controller` + `@ResponseBody`. 반환값을 **JSON 본문**으로 직렬화. REST API용. 제 프로젝트는 전부 `@RestController`.

### 14) `@Service` / `@Repository` / `@Component`
셋 다 `@Component`의 특수화로 빈 등록은 동일하지만 **역할(의미)을 명시**합니다.
- `@Component`: 일반 빈
- `@Service`: 비즈니스 로직 계층
- `@Repository`: 데이터 접근 계층 + **DB 예외를 Spring `DataAccessException` 으로 변환**해주는 부가 기능

### 15) 서버 실행 시 가장 먼저 실행되는 클래스
**`TechSyncApplication`** 의 `main()` → `SpringApplication.run()`.

### 16) `@SpringBootApplication` 역할
세 어노테이션의 묶음:
- `@SpringBootConfiguration`(설정 클래스)
- `@EnableAutoConfiguration`(의존성 기반 자동 설정)
- `@ComponentScan`(같은 패키지 이하 빈 스캔)
> 추가로 제 프로젝트는 `@EnableJpaAuditing`(생성/수정 시각), `@EnableScheduling`(뉴스 수집 스케줄러), `@EnableCaching` 도 켜둠.

### 17) GET vs POST
- GET: 조회. 파라미터가 URL(쿼리스트링)에 노출, 캐시·북마크 가능, 멱등/안전
- POST: 생성·변경. 데이터를 **본문(body)** 에 담아 전송, 캐시 안 됨. 로그인/회원가입처럼 민감하거나 상태를 바꾸는 요청에 사용

### 18) 상태코드 의미
- 200 OK(성공), 201 Created(생성 성공 — 회원가입 응답), 400 Bad Request(검증 실패),
- 401 Unauthorized(인증 안 됨/실패), 403 Forbidden(인증은 됐으나 권한 없음),
- 404 Not Found(리소스 없음), 500 Internal Server Error(서버 내부 오류)

### 19) 401 vs 403
- **401**: "너 누구인지 모르겠다" — 로그인/토큰이 없거나 유효하지 않음
- **403**: "너인 건 알겠는데 권한이 없다" — 인증은 됐지만 접근 불가

### 20) 프론트가 요청값 이름을 바꾸면 백엔드 수정 위치
해당 **요청 DTO의 필드명**(예: `LoginRequest`의 `email`). JSON 키와 DTO 필드명이 매칭되므로 그 필드(또는 `@JsonProperty`)를 맞춰야 합니다.

### 21) 사용한 외부 Open API
**네이버 검색(뉴스) API** — `https://openapi.naver.com/v1/search/news.json`

### 22) 사용 이유
키워드 기반 기술 뉴스 피드가 핵심 기능인데, 직접 크롤링은 불안정·법적 부담이 있어 **공식 검색 API**로 키워드별 최신 뉴스를 안정적으로 수집하기 위해서입니다.

### 23) 외부 API 호출 코드 위치
`service/NaverNewsCollectorService.java`

### 24) Controller 직접 작성? Service 분리?
**Service로 분리**했습니다. 컨트롤러가 아니라 `NaverNewsCollectorService` 가 `@Scheduled` 로 주기 실행되며 호출합니다(사용자 요청과 무관한 배치성 수집).

### 25) 호출 방식
**`RestTemplate`** 의 `exchange()` 로 GET 호출. 인증 헤더(`X-Naver-Client-Id/Secret`)를 실어 보냅니다.

### 26) API Key 저장 위치
`application.yml` 에 두되 **값은 환경변수**로 주입: `client-id: ${NAVER_CLIENT_ID}`. 실제 값은 `.env`(gitignore)에서 관리.

### 27) API Key를 GitHub에 올리면?
누구나 키를 도용 → **요금 폭탄/쿼터 소진/계정 정지** 위험. 한번 푸시되면 히스토리에 남아 삭제해도 노출된 것으로 간주하고 **즉시 재발급**해야 합니다.

### 28) application.yml 민감정보 보호
- 값을 직접 쓰지 않고 **환경변수 치환**(`${...}`)
- `.env`/실제 설정파일은 **.gitignore**
- 운영은 서버 환경변수/시크릿으로 주입

### 29) 외부 API 호출 실패 처리
`collectByKeyword()` 를 `try/catch` 로 감싸 실패 시 **에러 로그만 남기고 0건 반환**, 다음 키워드 수집은 계속 진행(한 키워드 실패가 전체 수집을 막지 않음).

### 30) 외부 API가 느리거나 무응답이면 화면 문제?
제 구조에선 수집이 **백그라운드 스케줄러**라 사용자 화면이 직접 멈추진 않습니다. 다만 새 기사가 안 들어와 **피드가 갱신되지 않습니다**. (만약 사용자 요청 시점에 동기 호출했다면 응답 지연/타임아웃으로 화면이 멈췄을 것.)

### 31) 타임아웃 처리 했나?
**현재 `RestTemplate` 에 별도 타임아웃을 설정하지 않았습니다(개선 포인트).** 운영 강화하려면 `RestTemplateConfig` 에서 `ClientHttpRequestFactory` 로 connect/read 타임아웃을 주는 게 맞습니다. 지금은 스케줄러 + try/catch라 실패해도 다음 주기에 재시도되는 구조로 위험을 낮췄습니다.

### 32) 호출 횟수 제한 대응
- 1시간 간격 스케줄(`fixedDelay = 3600000`)로 호출 빈도 자체를 낮춤
- `existsBySourceId` 로 **중복 기사 스킵** → 불필요한 저장/처리 감소
- (확장안) 키워드별 호출 간 간격 두기, 백오프/재시도, 캐싱

### 33) 응답 JSON → DTO 변환
`ParameterizedTypeReference<Map<String,Object>>` 로 받아 `items` 리스트를 순회하며 필요한 필드만 꺼내 `Article` 엔티티로 변환합니다(전용 응답 DTO 없이 Map 파싱).

### 34) 응답 중 DB에 저장하는 필드
`Article` 에 link(sourceId/link), title, description, keyword, pubDate(publishedAt), 그리고 source="NAVER", collectedAt. 제목/본문은 `stripHtmlTags()` 로 `<b>` 등 태그 제거 후 저장.

### 35) 전체를 저장하지 않고 필요한 값만 저장하는 이유
- 불필요한 필드까지 저장하면 **저장공간 낭비 + 스키마 결합도 증가**
- 외부 응답 포맷이 바뀌어도 내 도메인은 안정적으로 유지
- 화면에 필요한 값만 있으면 충분

## JPA 질문

### 1) `@Entity` 역할
클래스를 **DB 테이블과 매핑**되는 영속 객체로 지정. JPA가 이 클래스를 관리(영속성 컨텍스트) 대상으로 인식.

### 2) `@Id`, `@GeneratedValue`
- `@Id`: PK 필드 지정
- `@GeneratedValue(strategy=IDENTITY)`: PK 생성을 **DB AUTO_INCREMENT** 에 위임. `User.userId` 에 사용.

### 3) `@Column` 사용 이유
컬럼명/제약조건 매핑. 예: `@Column(name="USER_EMAIL", nullable=false, unique=true, length=100)` — 필드명과 다른 컬럼명, NOT NULL·UNIQUE·길이 제약을 지정.

### 4) findBy 메서드
`UserRepository.findByEmail(String)`, `findByName(String)`, `existsByEmail(String)`, `ArticleRepository.existsBySourceId(String)`, `KeywordRepository.findByKeywordName(String)` 등. 메서드 이름 규칙으로 쿼리가 자동 생성됩니다.

### 5) findByEmail 등은 어떤 SQL?
`findByEmail("x")` ≈ `SELECT * FROM USER_INFO WHERE USER_EMAIL = 'x'`. `findById` ≈ PK 조회 `WHERE USER_ID = ?`. `existsByEmail` ≈ `SELECT COUNT/EXISTS ... WHERE USER_EMAIL = ?`.

### 6) Optional 사용
`findByEmail` 이 `Optional<User>` 반환. **결과가 없을 수 있음을 타입으로 표현**해 NPE를 방지하고, `orElseThrow` 로 분기하기 위함.

### 7) orElseThrow 사용
`findByEmail(...).orElseThrow(() -> new BusinessException("...", UNAUTHORIZED))`. **조회 결과가 없을 때**(로그인: 없는 이메일, 재설정: 없는 계정) 예외 발생.

### 8) `@Transactional` 사용
- `signup`, `resetPassword`: 쓰기 트랜잭션(중간 실패 시 롤백 보장)
- `login`, `findEmailsByName`: `readOnly = true`(조회 최적화)
> 특히 `resetPassword` 는 변경감지(dirty checking)로 `updatePassword()` 후 트랜잭션 커밋 시 자동 UPDATE 되도록 `@Transactional` 이 필요.

### 9) save() 는 insert? update?
**둘 다.** 엔티티에 식별자(PK)가 없으면(신규) `insert`, 이미 영속/식별자가 있으면 `merge`(update)로 동작. 회원가입은 신규라 insert.

### 10) 컬럼명 변경 시 수정 위치
해당 Entity의 `@Column(name=...)` 값. (실제 컬럼명만 바뀌면 필드명은 그대로 두고 `name` 만 고치면 됨.)

### 11) `@Valid` 사용 DTO
컨트롤러 파라미터에 `@Valid @RequestBody` 로 적용. 대상 DTO: `SignupRequest`, `LoginRequest`, `FindIdRequest`, `ResetPasswordRequest`, `UpdateUserRequest` 등.

### 12) `@NotBlank` / `@NotNull` / `@Email` / `@Size`
- `@NotNull`: null 만 금지(빈 문자열 "" 은 통과)
- `@NotBlank`: 문자열 전용, null·""·공백 모두 금지
- `@Email`: 이메일 형식 검증
- `@Size(min,max)`: 길이/크기 범위 (예: 비밀번호 `@Size(min=8)`)

### 13) 예외 시 사용자 메시지
`GlobalExceptionHandler`(`@RestControllerAdvice`)가 일괄 처리:
- `BusinessException` → 지정한 상태코드 + 메시지("이메일 또는 비밀번호가 올바르지 않습니다." 등)
- 검증 실패(`MethodArgumentNotValidException`) → 400 + 첫 번째 필드의 메시지("비밀번호는 8자 이상이어야 합니다." 등)
- 응답은 항상 `ApiResponse` 포맷으로 통일.

## Spring Security 질문

### 1) 적용 이유
인증/인가를 표준화된 방식으로 처리하고, **JWT 필터·비밀번호 암호화·URL 접근제어**를 일관되게 적용하기 위해.

### 2) 인증 vs 인가
- 인증(Authentication): "**누구인가**" 확인(로그인, 토큰 검증)
- 인가(Authorization): "**무엇을 할 수 있는가**" 권한 확인

### 3) 비로그인 접근 가능 URL
`/api/auth/**`(로그인·회원가입·토큰재발급·아이디찾기 등), `/api/keywords`(추천 키워드 조회), `/ws/**`(WebSocket 핸드셰이크) — `SecurityConfig` 에서 `permitAll()`.

### 4) 로그인해야 접근 가능한 URL
위 화이트리스트를 제외한 **나머지 전부**(`anyRequest().authenticated()`). 예: `/api/users/me`, `/api/feed`, `/api/workspaces/**`, `/api/alarm`.

### 5) URL 권한 설정 파일
`config/SecurityConfig.java` 의 `securityFilterChain` 빈.

### 6) SecurityConfig 핵심 설정
- `csrf.disable()` — 토큰 기반이라 CSRF 불필요
- `sessionCreationPolicy(STATELESS)` — 세션 안 씀(JWT)
- `authorizeHttpRequests` — 화이트리스트 permitAll, 그 외 authenticated
- `addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)` — JWT 필터를 인증 필터 앞에 배치
- `PasswordEncoder` 빈 = `BCryptPasswordEncoder`

### 7) SecurityFilterChain 역할
요청이 거치는 **보안 필터들의 묶음(규칙)** 을 정의. 어떤 URL을 열고 막을지, 세션 정책, 커스텀 필터 위치 등을 설정.

### 8) requestMatchers() 역할
**특정 URL 패턴을 골라** 거기에 권한 규칙(permitAll/authenticated 등)을 매칭. 예: `requestMatchers("/api/auth/**").permitAll()`.

### 9) permitAll() vs authenticated()
- `permitAll()`: 인증 없이 누구나 접근
- `authenticated()`: **인증된 사용자만** 접근

### 10) hasRole() / hasAuthority() 사용?
**사용하지 않았습니다.** 제 서비스는 역할 구분(관리자/일반)이 없어 "로그인 여부"만 따지면 충분했습니다. (둘의 차이: `hasRole("ADMIN")` 은 내부적으로 `ROLE_` 접두사를 붙여 비교, `hasAuthority("ROLE_ADMIN")` 은 문자열 그대로 비교.)

### 11) 비밀번호 평문 저장?
아니요. **BCrypt 해시**로 저장합니다(`passwordEncoder.encode()`).

### 12) PasswordEncoder 역할
비밀번호를 **단방향 해시로 암호화**하고, 로그인 시 `matches(평문, 해시)` 로 일치 여부를 검증.

### 13) BCrypt 복호화 가능?
**불가능.** 단방향 해시 + salt 방식이라 원문 복원이 안 됩니다. 검증은 같은 입력을 다시 해싱해 비교.

### 14) 로그인 비밀번호 비교 위치
`AuthServiceImpl.login()` 에서 `passwordEncoder.matches(request.password(), user.getPassword())`.

### 15) CSRF 비활성화 이유
**세션·쿠키 기반이 아니라 JWT(헤더)** 인증이기 때문. CSRF는 브라우저가 쿠키를 자동 전송하는 점을 노리는데, 토큰을 헤더에 직접 실으므로 해당 위협이 적용되지 않습니다.

### 16) CORS가 왜 필요한가
브라우저는 **다른 출처(origin)** 로의 요청을 기본 차단(SOP)합니다. 프론트(다른 포트/도메인)에서 백엔드 API를 부르려면 서버가 CORS로 허용해줘야 합니다.

### 17) 프론트/백엔드 포트가 다르면?
출처가 달라 **CORS 차단**이 발생합니다. 제 프로젝트는 프론트 axios `baseURL` 을 상대경로 `'/api'` 로 두고, **운영은 nginx가 같은 도메인에서 프론트·API를 함께 서빙**(`/api`→백엔드 프록시)해 동일 출처로 만들었습니다. 그래서 별도 CORS 설정이 필요 없었습니다(로컬 개발은 dev 서버 프록시 사용).

## JWT 질문

### 1) 세션 기반? JWT 기반?
**JWT 기반.** `SessionCreationPolicy.STATELESS` 로 서버 세션을 쓰지 않습니다.

### 2) 세션 vs JWT
- 세션: 서버가 로그인 상태를 **메모리/저장소에 보관**(상태유지, stateful). 확장 시 세션 공유 필요
- JWT: 상태를 **토큰 자체에** 담아 서버가 검증만 함(stateless). 수평 확장 쉬움. 대신 발급 후 무효화가 어려움(→ 제 프로젝트는 refresh를 Redis로 관리해 보완)

### 3) JWT 구조
`Header.Payload.Signature` — 점(.)으로 구분된 3부분.

### 4) Header / Payload / Signature 역할
- Header: 토큰 타입, 서명 알고리즘(HS256 등)
- Payload: 클레임(사용자 정보·만료시간 등)
- Signature: Header+Payload를 비밀키로 서명한 값 → **위변조 검증**용

### 5) Payload에 넣은 정보
`subject = userId`, `email` 클레임, 발급시각(iat), 만료시각(exp). (`JwtProvider.buildToken`)

### 6) Payload에 비밀번호 금지 이유
Payload는 **암호화가 아니라 Base64 인코딩**이라 누구나 디코딩해 볼 수 있습니다. 비밀번호·민감정보를 넣으면 그대로 노출됩니다.

### 7) JWT는 암호화? 인코딩?
**인코딩(+서명).** 내용은 Base64URL로 인코딩되어 읽을 수 있고, 서명으로 위변조만 막습니다(기밀성 X, 무결성 O).

### 8) Access vs Refresh Token
- Access: **API 호출 인증**용, 짧은 수명(30분)
- Refresh: Access 만료 시 **재발급**용, 긴 수명(7일)

### 9) Access Token 용도
매 API 요청 헤더에 실어 **본인 인증**. JwtFilter가 검증.

### 10) Refresh Token 용도
Access가 만료됐을 때 **재로그인 없이 새 Access를 발급**받는 용도.

### 11) Access Token 발급 시점
로그인 성공 시, 그리고 refresh 재발급 시.

### 12) Refresh Token 발급 시점
로그인 성공 시 함께 발급, 재발급(`/refresh`) 시 새 것으로 회전(rotation).

### 13) Access 만료시간
`jwt.access-expiration: 1800000` ms = **30분**.

### 14) Refresh 만료시간
`jwt.refresh-expiration: 604800000` ms = **7일**. Redis 저장 TTL도 동일하게 설정.

### 15) Access를 너무 길게 잡으면?
탈취 시 **장시간 악용**됩니다. 무효화가 어려운 JWT 특성상 피해가 커지므로 짧게(30분) 두고 refresh로 보완.

### 16) Refresh 탈취되면?
공격자가 Access를 계속 재발급받아 **장기간 사칭** 가능. 그래서 Redis에 저장·대조하고, 비밀번호 재설정/로그아웃 시 **삭제(무효화)** 하도록 했습니다.

### 17) Access 저장 위치(프론트)
브라우저 **localStorage**(`access_token`).

### 18) Refresh 저장 위치
- 서버: **Redis** (`refresh:{userId}`)
- 클라이언트: localStorage(`refresh_token`)

### 19) Access를 localStorage에 두면 보안 위험?
**XSS 취약**합니다. 악성 스크립트가 localStorage를 읽어 토큰을 탈취 가능. (대안: httpOnly 쿠키 — 단 CSRF 고려 필요. 데모 범위라 localStorage 채택.)

### 20) Refresh를 Redis에 저장하는 이유
- **서버 측 무효화**가 가능(로그아웃/비번 재설정 시 삭제 → 그 토큰 무력화)
- 저장된 값과 **대조**해 탈취·재사용 탐지
- TTL로 자동 만료 관리, 빠른 조회

### 21) 로그인 성공 후 JWT 발급 흐름
사용자 검증 → `createAccessToken`/`createRefreshToken` → Redis에 refresh 저장(TTL 7일) → `AuthResponse` 로 두 토큰 반환 → 프론트가 저장.

### 22) API 요청 시 JWT 위치
HTTP 요청 헤더 `Authorization: Bearer {accessToken}`. (프론트 axios 인터셉터가 자동 부착.)

### 23) Bearer 의미
"이 토큰의 **소지자(bearer)** 에게 권한을 부여한다"는 인증 스킴. 토큰을 가진 자가 곧 인증 주체라는 뜻.

### 24) JWT 검증 위치 — Controller? Filter?
**Filter** (`JwtFilter`, `OncePerRequestFilter`). 컨트롤러 도달 전에 검증해 인증 컨텍스트를 세팅합니다.

### 25) JWT Filter 역할
요청 헤더에서 Bearer 토큰 추출 → `JwtProvider.isValid()` 검증 → 유효하면 **SecurityContext에 인증 객체 등록**. 이후 컨트롤러는 인증된 사용자로 처리.

### 26) 검증 후 SecurityContext에 저장하는 것
`UsernamePasswordAuthenticationToken(userId, email, 권한목록)`. principal로 **userId**, credential로 email을 담음(권한 목록은 비어 있음).

### 27) SecurityContext에 저장하는 이유
이후 요청 처리 동안 **인증 상태를 공유**하기 위해. Security가 이를 보고 인가 판단을 하고, 컨트롤러/서비스에서 현재 사용자(userId)를 꺼내 쓸 수 있습니다.

### 28) Access 만료 시 사용자 처리
검증 실패 → 인증 컨텍스트 미설정 → 보호 API가 401/403 응답 → 프론트 axios 인터셉터가 이를 잡아 **refresh로 1회 자동 재발급** 후 원요청 재시도. refresh도 실패하면 로그아웃 처리(로그인 페이지로 이동).

### 29) Refresh로 Access 재발급 API 있나?
있습니다. `POST /api/auth/refresh` (`Refresh-Token` 헤더로 전달).

### 30) 재발급 API 동작 흐름
1. `Refresh-Token` 헤더 수신
2. 토큰 서명/만료 유효성 검증(`isValid`)
3. `userId` 추출 → Redis의 `refresh:{userId}` 값과 **일치 확인**
4. 일치하면 새 Access/Refresh 발급, Redis 값도 새 것으로 갱신(회전)
5. `AuthResponse` 반환. 불일치/없음이면 401.

### 31) Refresh가 DB(Redis) 저장값과 다르면?
`BusinessException("유효하지 않은 토큰입니다.", 401)` 로 거부. (이미 회전됐거나 로그아웃된 옛 토큰 → 재사용 차단.)

### 32) 로그아웃 시 토큰 처리
`POST /api/auth/logout` → 서버는 **Redis의 refresh 토큰 삭제**(재발급 불가화). Access는 stateless라 서버가 즉시 폐기할 수 없어 **남은 만료시간까진 유효**하지만, 프론트가 localStorage에서 제거하고 refresh가 없으니 만료 후 갱신 불가 → 사실상 로그아웃 완료.

## 보조 핵심 흐름 — SSE 실시간 알림 (Redis Pub/Sub + MongoDB)
> 알림은 **SSE(서버→클라 단방향 push) + Redis Pub/Sub(서버 간 전파) + MongoDB(영속화)** 조합. "동시 편집은 양방향이라 WebSocket, 알림은 단방향이라 SSE" 처럼 요구사항에 맞춰 프로토콜을 다르게 선택한 점이 어필 포인트.

**① 구독(SSE 연결)**
1. 로그인 후 프론트가 `GET /api/alarm/subscribe`(`Accept: text/event-stream`)로 연결
2. `AlarmController.subscribe(@AuthenticationPrincipal userId)` → `AlarmServiceImpl.subscribe()`:
   - `SseEmitter`(30분 타임아웃) 생성, `SseEmitterRepository`(인메모리 ConcurrentHashMap)에 userId별 저장(멀티탭 다중 emitter 허용)
   - `onCompletion/onTimeout/onError` 에서 emitter 정리(누수 방지)
   - 연결 직후 더미 `connect` 이벤트로 프록시 버퍼 flush + 브라우저 `onopen` 트리거

**② 알림 발생(발행)**
3. 트리거(멤버 초대, 키워드 뉴스 도착 등)에서 `alarmService.notify(targetUserId, type, message, workspaceId)`:
   - **MongoDB `Alarm` 저장**(read=false) → 영속화(오프라인 사용자도 재접속 시 조회)
   - `AlarmEvent` JSON 직렬화 → **Redis `alarm` 채널 `convertAndSend`**(Pub/Sub 발행)
   - 발행 실패해도 DB에 남아 다음 조회 시 노출(graceful degradation)

**③ 전파(Redis 구독 → 로컬 emitter)**
4. 모든 서버 인스턴스가 `RedisMessageListenerContainer` 로 `alarm` 채널 구독 → `dispatchToLocalEmitters(event)`:
   - `SseEmitterRepository` 에서 targetUserId의 emitter 조회 → `event().name("alarm").data(alarm)` 전송(실패 시 정리)

**④ 클라이언트 수신**
5. 브라우저 `EventSource` 가 `alarm` 이벤트 수신 → 토스트/안읽음 배지 갱신

**⑤ 보조 REST**
6. `GET /api/alarm`(목록), `/unread-count`(안읽음 수), `PATCH /{alarmId}/read`(읽음 처리, 본인 것만 — 아니면 403)

**설계 포인트**: SSE = 단방향 push에 적합(HTTP 기반·자동 재연결) / `SseEmitterRepository` 는 인스턴스 로컬 인메모리라 다중 인스턴스에선 누가 어느 서버에 붙었는지 모름 → **Redis Pub/Sub로 전 서버에 전파**해 수평 확장 대응 / 알림 영속화는 MongoDB가 담당해 역할 분리.

## 핵심 한 줄 요약 (말문 막힐 때)
- **인증 구조**: JWT(Access 30분/Refresh 7일), Refresh는 Redis 저장→무효화 가능, 검증은 JwtFilter에서.
- **계층**: Controller(입출구)–Service(로직·트랜잭션)–Repository(JPA)–Entity(테이블), DTO로 입출력 분리.
- **외부 API**: 네이버 뉴스 검색을 RestTemplate로 스케줄 수집, 키 환경변수, 실패는 로그+스킵.
- **보안**: BCrypt 해시, stateless+CSRF off, URL 화이트리스트 외 인증 필수.
- **개선 인지 포인트**: RestTemplate 타임아웃 미설정, Access를 localStorage 저장(XSS) — 트레이드오프를 알고 선택했다고 답할 것.
